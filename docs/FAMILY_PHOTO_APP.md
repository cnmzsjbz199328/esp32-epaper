# 全家福渐显应用设计

目标板卡：Waveshare ESP32-S3-Touch-ePaper-1.54（200x200，1bpp）
硬件基线：`epaper_154 v0.7.10`，提交 `d5221ec6356fc4d0b419157cf4198ae5c1d5295b`
硬件事实以 [EPAPER_154_APP_GUIDE.md](EPAPER_154_APP_GUIDE.md) 为准，本文只写应用设计。

## 一句话定义

上电后全刷一次背景图；此后每点一下屏幕，用**局部刷新**在背景上叠加出一个家庭成员，直到全家福完整。

参考项目 `itopinion/zectrix-note4-epd-demo` 的其余功能（Wi-Fi 扫描、RTC、音频、设备信息）在本项目里只做**最小可测版本**，验收标准是"页面能出、串口不报错"，不追求完整度。局部刷新是唯一需要做扎实的部分。

## 为什么这个场景适合局刷

- 每一步基本只有**新增黑色像素**，白转黑是局刷 LUT 最擅长的方向，残影风险最低。
- 背景在整个过程中不变，天然就是局刷要求的"基准图"。
- 交互是低频点击，完全不需要动画帧率。

反过来说，如果后续想加"撤销上一个人"（黑转白），残影会明显得多，那一步应该直接走全刷。

**但"只加黑"不是自动成立的**，见下面的背景约束。人物身上的白色区域（脸、浅色衣服）落在深色背景上时，局刷必须把已有的黑像素擦成白，那正是残影最重的方向。这个问题在拍摄和选背景阶段就要解决，软件补救不了。

## 显示流程

```text
上电
 └─ bsp_board_init() / bsp_ui_init() / bsp_touch_init()
 └─ 背景图写入 framebuffer
 └─ 全刷 (0x22 0xC7)                          约 1755ms
 └─ bsp_ui_partial_begin()
      ├─ 硬复位 + 下发 WF_PARTIAL_1IN54_0
      ├─ 0x37 十字节 / 0x3C border 0x80 / 0x22 0xC0
      └─ 基准图：0x24 和 0x26 各写一遍当前 framebuffer
 └─ 循环：
      触摸 → 在 framebuffer 上叠加第 N 个人 → bsp_ui_flush_partial()
                                              (只写 0x24 + 0x22 0xCF)
 └─ 全员出齐 → 一次全刷定格 → 可选长按 PWR 清屏关机
```

关键点：**framebuffer 是唯一真值**。每次局刷都把整帧 5000 字节重新推给 `0x24`，不做窗口寻址。人物之间的遮挡关系由绘制顺序决定，不需要驱动层参与。

## 残影管理

局刷的残影阈值在这块板上没有实测数据，先按保守策略写死，再用实物调：

```cpp
#define APP_PARTIAL_MAX_STREAK 6   /* 连续局刷上限，超过则插一次全刷 */
```

插全刷时必须重新走一遍 `bsp_ui_partial_begin()`，因为全刷会换掉 LUT，也会让 `0x26` 里的旧帧失效。

另外，出于观感考虑，**最后一个人出完后必须做一次全刷**。局刷叠出来的画面对比度略低于全刷，一次全刷定格能让最终的全家福干净收尾，而且断电保图的也是这一帧。

## 素材：双位平面

墨水屏没有 alpha 通道，而绿幕抠出的人物是不规则轮廓。所以**每个人物需要两个位平面**，只给 `bits` 是不够的：

```cpp
typedef struct {
    const char*    name;
    int            x, y, w, h;
    const uint8_t* bits;   /* 1 = 这里是黑墨 */
    const uint8_t* mask;   /* 1 = 这个像素属于人物 */
} app_person_t;

extern const app_person_t APP_PERSONS[];
extern const int APP_PERSON_COUNT;
extern const uint8_t APP_BACKGROUND[5000];
```

两个平面同样布局：1bpp、行优先、每行按 8 像素/字节补齐。叠加运算是逐字节的三操作数混合：

```text
fb = (fb & ~mask) | (bits & mask)
```

没有 `mask` 就分不清"人物身上的白色衣服"和"人物轮廓外的背景"，结果是把整个矩形框糊到画面上。因此 `bsp_ui_draw_bitmap()` 从一开始就要带 mask 参数，不能事后补。

两条几何约束：

- 人物位图的 `x` 和 `w` **建议按 8 对齐**。整帧局刷不要求这个，但将来若改窗口局刷就是硬约束，现在对齐等于免费买保险。
- 素材全部编译进 Flash，不走 SD 卡。一个 96x128 的人物双平面约 3KB，8 个人 24KB，加背景 5KB 共约 30KB，是 8MB Flash 的 0.4%。SD 卡在容量上毫无必要，却引入挂载失败、文件损坏、读取延迟三条新的出错路径。真实价值只有"换照片不用重烧录"，那属于 M5，等局刷跑通再说；素材的二进制布局按 Flash/SD 通用来设计，到时候只换加载来源，上层代码不动。

## 背景约束（硬约束，不是建议）

**背景图在人物落点区域必须尽量浅。**

局刷 LUT 能做黑→白，但残影明显重于白→黑。人物身上的白色区域（脸、浅色衣服）如果落在深色背景上，每次局刷都要擦掉一片黑，残影会直接暴露。

- 理想：浅天空、白墙、浅色地面、纯色/浅纹理生成图。
- 最差：深色树林、夜景、大面积暗部。
- 如果背景在人物落点处本来就是白的，整个流程退化成"纯加黑"，画质和残影同时取到最优。

这不是软件能补救的，是拍摄和选背景时就要定的事。若实拍背景在人物落点处偏暗，只有两条路：换背景，或在转换工具里对该区域做提亮。

## 素材管线

```text
assets/src/          绿幕原图（不进 git，.gitignore 已排除）
  bg.jpg
  person_01.jpg ...
assets/layout.json   每个人的 x/y/缩放/出场顺序/遮挡层级
tools/img2c.py       转换工具
assets/generated/    产物：family_assets.c / .h + preview.png
```

`tools/img2c.py` 在 PC 上跑，做四件事：

1. 色度键抠图（绿幕 → mask）
2. 边缘去绿边
3. 缩放并摆到 `layout.json` 指定的位置
4. 抖动成 1bpp 双平面 C 数组

同时输出一张合成预览 PNG，在电脑上就能看到最终屏幕效果，不烧板子也能反复调素材。`layout.json` 是调构图的地方，改完重跑工具看预览，这是整个流程里迭代最快的环节。

拍摄要点：光要匀（绿布上不能有明显阴影）；人和绿布拉开距离（避免绿光反射到脸和衣服上形成绿边）；不要穿绿色或浅色反光衣物。

**出场顺序与遮挡**：人物重叠时后绘制的盖住先绘制的，由绘制顺序天然决定，驱动层不参与。但在 `layout.json` 里要想清楚——被挡住的人应该先出场。

**画质的现实预期**：200x200 屏幕上一个人物大概只有 100~130 像素高、60 像素宽，这个尺寸留不住五官细节。建议人少一点、大一点（4~6 人明显好于 10 人）。工具提供两种渲染模式供对比：Floyd-Steinberg 抖动（有灰度感，近看是噪点）和高对比阈值（像剪影版画，更干净）。这个选择很主观，看预览再定。

## 交互

沿用基础测试项目已验证的左右半屏约定：

| 动作 | 效果 |
|---|---|
| 触摸右半屏 | 下一个人出现（局刷） |
| 触摸左半屏 | 回到"只有背景"状态（全刷重来） |
| 长按 PWR 3 秒 | 清屏关机 |

左半屏刻意不做"撤销一个人"，因为那是黑转白，残影代价高，收益低。

触摸必须去抖：`bsp_touch_read()` 给的是 raw 坐标，没有事件队列。等按下 → 等抬起 → 再延时 180ms，模式见指南 L124-137。局刷期间要忽略触摸输入，否则会在 BUSY 中途重入。

## 里程碑

| 阶段 | 内容 | 验收 |
|---|---|---|
| M0 | 工程骨架：迁移 `boards/epaper_154/` + `lib/bsp_api` + `lib/bsp_core`，关掉 `BSP_EPAPER_INTERACTIVE_TEST_APP` 但保留自检作为诊断模式；补 `bsp_ui_fb()` / `bsp_ui_fb_clear()` / `bsp_ui_draw_bitmap()`（带 mask），用写死的测试图走全刷 | 屏上肉眼可见，串口无 FAIL |
| M1 | 实现 `bsp_ui_partial_begin/flush_partial/partial_end`，做一个"方块每次右移 20px"的最小局刷验证 | **实测并记录局刷 BUSY 毫秒数**；确认无全屏闪黑；连续 20 次观察残影何时可见，定出 `APP_PARTIAL_MAX_STREAK` |
| M2 | 打通 `tools/img2c.py` + `layout.json`，接入真实素材，实现完整的触摸叠加流程 | 预览 PNG 与实屏一致；全家福能一步步出齐 |
| M3 | 残影策略调参 + 结尾全刷定格 | 连续跑 3 轮不出现可见残影 |
| M4 | 补最小版 Wi-Fi 扫描 / RTC / 设备信息页 | 各页能出、串口无异常 |
| M5 | （可选）素材改从 SD 卡加载，支持随时换全家福 | 换卡换图，上层代码不动 |

M1 是整个项目的技术分水岭，**不要跳过它直接做 M2**。用方块位移验证局刷，出问题时只有驱动一个变量；混进真实素材以后，画面不对可能是 LUT、可能是基准图、也可能是素材转换错了。

M0 和 M1 都不依赖真实照片，可以在素材到位之前先跑完。

## 风险

| 风险 | 说明 | 处置 |
|---|---|---|
| 局刷 LUT 不生效 | 表来自官方 LVGL 示例，不是本板实测 | 用 BUSY 时长判据：局刷若仍是 ~1755ms，说明 LUT 没换掉 |
| 基准图不同步 | `0x26` 里的旧帧与实际画面不一致会导致鬼影 | 每次全刷后强制重走 `partial_begin()` |
| 残影累积 | 阈值未知 | M3 阶段实测，先按 6 次保守设定 |
| 抖动图观感差 | 200x200 1bpp 细节有限 | 人少而大（4~6 人），工具里对比抖动/阈值两种模式后再定 |
| 人物白区擦不干净 | 背景在落点处偏暗，局刷要做黑→白 | 拍摄阶段选浅背景；已拍则换背景或在工具里提亮该区域 |
| 绿边残留 | 绿光反射到脸/衣服 | 拍摄时人与绿布拉开距离；工具做边缘去绿边 |

## 排错

现象与首查项，在指南的排错表基础上补充：

| 现象 | 先查 |
|---|---|
| 局刷时整屏闪黑 | LUT 没换成 `WF_PARTIAL_1IN54_0`，或误用了 `0x22 0xC7` |
| 局刷后画面残留上一帧轮廓 | 基准图 `0x26` 未写或已失效 |
| 人物是个白/黑矩形块 | `mask` 平面未生成或未参与叠加，退化成整块 blit |
| 人物位置偏移或错位 | 位图行未按 8 像素补齐，或 x 起点未对齐 |
| 点一下出现两个人 | 触摸去抖缺失，或局刷 BUSY 期间未屏蔽输入 |

原则不变：应用现象与基础测试结论冲突时，先回 `esp32_test` 复测硬件。
