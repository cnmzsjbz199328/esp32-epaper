# 经典文学有声电纸书故事库扩展计划

## 1. 目标

在现有 `FOX_FOREST` 端到端故事包跑通的基础上，扩展为一个适合
Waveshare ESP32-S3 Touch ePaper 1.54（200x200、1bpp）的经典文学有声故事库：

- 用户进入故事应用后先看到统一的故事选择列表。
- 原有 `PHOTOS`、内置 `FOX_FOREST`、SD 卡故事彼此并列，不互相覆盖。
- 选择某个故事后，按场景显示图片并播放同编号台词音频。
- 每个故事都可以独立生成、试听、替换、打包和回滚。
- 图片在 200x200 小尺寸墨水屏上保持清晰，禁止“整块过黑背景”吞掉细节。

本计划只覆盖内容库、资产管线、故事选择和硬件验收；暂不引入联网下载、云端账户
同步、复杂 CJK 字体或连续背景音乐。

## 2. 内容方向与首批故事

首批采用公版原作，但所有中文台词都使用原创改写，不直接复制现代译本。荷马和
莎士比亚的原作属于公版范围；具体中文译文、插图和音频仍必须由本项目独立创作。

默认定位为全年龄段、可偏成人向的“完整情节压缩改写”，不是逐字完整翻译，也不
定义为儿童专属。每个故事必须保留主要人物关系、核心冲突、关键转折、结局和主题
余韵；涉及战争、死亡、恐怖或爱情悲剧时，采用克制但不回避因果的叙述，并在
`story.json` 标明年龄建议。

### 第一批建议

| ID | 原作 | 叙事切口 | 建议场景数 | 视觉重点 |
| --- | --- | --- | ---: | --- |
| `odyssey_homecoming` | 荷马《奥德赛》 | 漫长归航、代价、认出故乡与复归 | 14 | 海面、船、星空、故乡门廊；夜空保持白底留白 |
| `midsummer_dream` | 莎士比亚《仲夏夜之梦》 | 欲望、误会、权力关系与和解 | 14 | 树林用稀疏线条表现，不使用黑色森林墙 |
| `tempest_island` | 莎士比亚《暴风雨》 | 风暴、流放、权力、魔法与宽恕 | 14 | 风暴用弧线、雨线和白色负空间表现 |
| `romeo_juliet_balcony` | 莎士比亚《罗密欧与朱丽叶》 | 家族冲突、相爱、选择与悲剧后果 | 12 | 夜景用白色天空、建筑轮廓和少量阴影，不做黑色满幅背景 |

第一阶段先完成前三个故事；`romeo_juliet_balcony` 作为第二阶段候选，避免首批
同时引入过多悲剧内容和音频制作量。

每个故事先做约 12–16 个场景，目标约 14 个。一个场景只表达一个清晰动作、冲突
升级或情绪转折，单段中文旁白目标为 45–110 字、约 10–30 秒。场景数量增加是为了
补足因果链，不是把多个地点、角色和事件硬塞进同一段；每个故事仍须有清晰开端、
发展、转折、高潮与结局。

当前已生成的六场景图片包视为“关键帧基础资产”：可以复用，但必须重新映射到扩展
后的场景编号，并在关键冲突、转折和结局之间补充图片。旧六场景脚本和音频不得与
扩展脚本混用；在新脚本冻结前暂停批量 TTS。

## 3. 统一目录和数据契约

每个故事都遵循现有 `fox_forest` 结构：

```text
assets/stories/<story_id>/
├─ build.json
├─ README.md
├─ <story_id>.fvid
├─ <story_id>_preview.png
├─ source/
│  ├─ scenes/000.png ...
│  └─ audio_<provider>/000.wav ...
└─ <story_id>/
   ├─ story.json
   ├─ ai_studio_script.md
   └─ audio/000.wav ...
```

`story.json` 必须至少包含：

```json
{
  "version": 1,
  "id": "midsummer_dream",
  "title": "仲夏夜之梦",
  "author": "William Shakespeare",
  "language": "zh-CN",
  "age_rating": "全年龄/12+",
  "voice": "Gemini 3.1 Flash TTS Preview / Achernar",
  "audio_format": "16kHz/16bit/mono PCM WAV",
  "scenes": [
    {
      "index": 0,
      "title": "森林入口",
      "narration": "原创中文旁白……",
      "audio": "audio/000.wav",
      "image": "../source/scenes/000.png"
    }
  ]
}
```

约束：

1. `index` 必须从 0 连续递增，图片、台词和音频使用同一个编号。
2. `narration` 必须与 `ai_studio_script.md` 的台词正文逐字一致。
3. 最终音频必须是单声道、16 kHz、16-bit PCM WAV；获批准的 TTS 工具下载的原始
   文件可按提供商保存在 `source/audio_<provider>/`，但不能直接作为固件播放文件。
4. 文件名只使用 ASCII 小写、数字、下划线和连字符，避免 SD 卡路径兼容问题。
5. `build.json` 记录 `frames_dir`、`glob`、`threshold`、`despeckle` 等可重建参数。
6. 故事包 README 记录原作、公版判断、中文改写说明、声音来源和资产生成命令。

## 4. 图片设计契约：优先保证墨水屏可读性

### 4.1 生成提示词的固定要求

所有图片生成 agent 都必须在基础提示词中写明：

```text
200x200 monochrome e-paper illustration, clear black ink line art on a mostly white
paper background, strong readable silhouettes, sparse hatching, large simple shapes,
one main subject, no text, no border, no watermark, no gradients, no photorealism,
no solid black background, no full-bleed dark sky, no black vignette, no dense dark fog,
leave generous white negative space around the subject, designed to survive 1-bit
thresholding on a small 200x200 e-ink display.
```

根据具体场景补充角色、动作和地点。不要让模型自行决定“电影感黑色背景”；夜晚、
洞穴、暴风雨和森林都必须通过轮廓、少量阴影、稀疏线条和留白表达。

### 4.2 可量化验收指标

在生成原图和最终 FVID 预览后都要检查：

- 画布固定为 200x200，最终 1bpp 黑色像素比例目标为 8%–32%。
- 黑色像素比例超过 38% 必须人工复核，超过 45% 直接退回重做。
- 少于 5% 时通常说明主体过淡或细节丢失，也必须人工复核。
- 主体至少占画面短边的约 35%，关键动作不能小于约 25x25 像素。
- 每个场景最多 1 个主主体和 2 个辅助主体；不要堆叠大量小人物、树叶、星星或建筑细节。
- 最终画面中，背景应以白色负空间为主；不得出现从边缘贯穿到边缘的整块黑场。
- 重要轮廓尽量达到 2–4 像素的最终线宽，避免 1 像素灰细线在阈值化后消失。
- 不在图片中生成标题、对白、字幕、装饰边框或水印；标题由 UI 或故事清单负责。

### 4.3 场景构图规则

每个场景提交前回答三个问题：

1. 读者在 1 秒内能否说出“谁在做什么”？
2. 缩小到 200x200 并转为黑白后，主体轮廓是否仍然完整？
3. 如果去掉所有阴影，只保留轮廓和留白，故事动作是否仍可理解？

建议构图：白色天空/墙面/地面 + 黑色轮廓主体 + 少量局部阴影。对于月夜、海上、
森林等场景，采用“白底夜景”策略：用弯月、细树枝、波浪线和少量黑色剪影暗示环境，
而不是把天空或背景涂成黑色。

## 5. 音频制作契约

每个故事创建一份 `ai_studio_script.md`，分成“全局声音指导词”和逐场景台词正文。
推荐流程：

1. 先写完 `story.json` 的 `narration`，再复制到台词脚本，避免先生成音频后改文字。
2. 使用统一的中文普通话声音方向，语速略慢、停顿自然、情绪克制。
3. 每次只生成一个场景；下载后立即重命名为 `000.wav`、`001.wav` 等。
4. 保留获批准的 TTS 工具原始下载文件到 `source/audio_<provider>/`，记录提供商、
   模型、音色、来源文件名和时长；不制作本机 SAPI 等备用音频。
5. 使用 `ffmpeg` 转换为 16 kHz、16-bit、单声道 PCM WAV，输出到故事的 `audio/` 目录。
6. 播放检查必须覆盖：开头没有被截断、结尾完整、切换场景时旧音频停止、新音频从头开始。
7. 不默认加入背景音乐和音效；如果以后加入，必须先验证不会遮盖人声和不会造成音频切换残留。

音频质量门槛：

- 旁白可懂度优先于戏剧化表演；中文停顿不能把一句话切成奇怪的短句。
- 单场景建议不超过 25 秒；更长内容拆成两个场景，而不是让画面长时间停留后再突然切换。
- 音频时长必须写入来源记录，`story.json`、文件名和场景顺序必须一致。
- 生成或替换音频后必须重新运行 ROM 压缩资源工具，并重新编译；不能只替换 WAV 文件后假设固件已更新。

## 6. 固件与故事库架构

### 6.1 当前实现需要保持的原则

- `PHOTOS`、内置故事和 SD 故事属于同一个故事列表。
- 选择列表只保存“故事条目”，进入播放页后再根据条目选择 ROM 或 SD 数据源。
- 当前选中的故事必须携带自己的帧数、帧源和音频映射；不能用全局单例音频数组覆盖其他故事。
- 场景切换仍遵守“显示刷新成功后才启动/切换音频”的现有规则。
- SD 卡不可用时，内置故事仍可播放；SD 故事读取失败时只回落到明确的内置兜底，不改变列表中的其他条目。

### 6.2 从单个内置故事升级为目录

当前 `FOX_FOREST` 已经通过独立 ROM 数组工作，但扩展多个内置故事时不要继续在
`app_family_video.cpp` 中硬编码更多 `if`。建议新增一个内置故事目录层：

```text
story_catalog.h/.cpp
├─ builtin story metadata
├─ builtin frame source lookup
├─ builtin audio source lookup
└─ story id -> library entry mapping
```

目录条目至少包含：`id`、显示名、场景数、帧源、音频源、音频场景数和存储类型。
`fvid_entry_t` 需要携带 `kind` 与 `builtin_index`（或等价字段），SD 路径仍单独保存。

建议存储策略：

- ROM 只保留 `PHOTOS` 和一个硬件验收故事 `FOX_FOREST`，保证无 SD 卡也能演示。
- 新增的经典故事默认打包到 SD 卡 `/video/`，由统一列表动态扫描。
- 只有在 flash 使用率和启动内存都通过验收时，才把第二个新故事加入 ROM demo profile。
- 不把多个长音频全部静态嵌入应用固件；当前单个故事已经明显增加 flash，未来应优先使用 SD。

### 6.3 选择列表交互

目标行为：

1. 进入故事应用总是先进入列表；列表至少显示 `PHOTOS` 和 `FOX_FOREST`。
2. 有 SD 卡时，将有效 `.fvid` 故事追加到列表；无卡时不隐藏内置条目。
3. 点击列表项或按 `ENTER` 后进入对应故事；`BACK` 返回列表，`HOME` 返回启动器。
4. 列表显示稳定的 ASCII `id` 和场景数，避免当前 5x7 字体无法显示中文造成乱码。
5. 列表分页和局部刷新不能改变故事顺序；新增故事不会覆盖已有条目。
6. 串口日志必须打印列表数量、选中故事 ID、数据源（ROM/SD）和当前场景编号。

## 8. Agent 分工建议

### 内容 agent

负责原作梗概、年龄分级、原创中文台词和场景编号。不得直接复制现代中文译本，
不得修改图片/音频文件名来“碰巧对齐”。交付前先提交 `story.json` 与台词脚本。

### 图片 agent

负责生成和筛选场景图片。必须遵守白底、低黑度、粗轮廓、少主体规则，并提交每帧
200x200 预览及黑色像素比例。发现整块黑背景、主体过小或阈值化后细节消失时，
必须重生成，而不是要求固件用算法补救。

### 音频 agent

负责根据 `ai_studio_script.md` 逐段生成、下载、重命名、格式转换和试听。每个故事
独立选择人声。交付时提交原始文件映射、最终 WAV 格式和时长表；不要制作本机备用
音频，也不要直接覆盖来源文件。

### 固件 agent

负责统一故事目录、ROM/SD 类型隔离、列表交互和串口日志。不得把新的故事做成
覆盖旧故事的编译期宏；不得在 SD 故事播放失败时静默切换到另一个故事的音频。

### 验收 agent

负责运行构建、烧录、串口采集和实机检查。重点检查：列表是否出现、选择后是否进入
正确故事、每帧是否播放对应音频、音频是否完整、返回和再次进入是否仍然正确。

## 9. 验收标准（Definition of Done）

一个新故事只有同时满足以下条件才能合并：

1. 故事包结构完整，`story.json`、图片和音频编号连续且引用一致。
2. 所有最终图片为 200x200，黑色像素比例符合第 4 节要求，contact sheet 在 1:1 查看时主体可辨。
3. 所有最终音频通过 16 kHz/16-bit/mono PCM 检查，首尾完整，无中途截断。
4. 无 SD 卡时，内置列表仍能正常显示且不影响 `PHOTOS` 与 `FOX_FOREST`。
5. 有 SD 卡时，新故事出现在同一列表，不覆盖内置故事或其他 SD 故事。
6. 选择新故事后，至少验证首场景、一个中间场景、最后场景和返回列表。
7. 固件日志没有 `FAIL`、`WARN`、`panic`、`abort`、`Guru Meditation` 或复位异常；现有第三方宏重定义警告需单独记录，不得新增。
8. `pio run -e epaper_154_app` 和硬件验收环境都能成功编译；如果修改了 ROM 资源，必须重新烧录并记录 flash 使用率。
9. 提交说明包含故事 ID、资产来源、生成命令、测试环境、串口摘要和实机照片/视频。

## 10. 推荐执行顺序

先完成 Phase 0 和 Phase 1，再制作第一个 `odyssey_homecoming` SD 故事包；确认故事
列表和源隔离稳定后，批量制作另外两个故事。图片和音频可以并行生产，但必须在进入
`C2-6` 前冻结 `story.json` 台词，防止画面、语音和元数据在最后阶段错位。

本计划的核心取舍是：内容可以不断增加，但 ROM 只承担稳定的演示和兜底；经典故事库
的扩展容量交给 SD 卡，故事选择交给统一列表，图片则以 200x200 墨水屏的可读性作为
第一优先级。
